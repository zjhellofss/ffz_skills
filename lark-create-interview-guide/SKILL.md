# 飞书技术面经生成

将指定飞书技术章节转换为“问题—面试回答—原文定位”一一对应的面经文档。优先保证原文保真、事实正确和链接可追溯，再优化口述性与版式。

## 必须加载的能力

1. 完整阅读并使用 `lark-doc` skill；遇到认证或权限问题时再阅读 `lark-shared`。
2. 若原文包含嵌入 Sheet、Base 或画板且其内容属于目标章节，按 `lark-doc` 的路由规则调用对应的 Lark skill 读取，不得仅凭占位块猜测内容。
3. 若存在与技术主题匹配的审校 skill，使用它核对事实。例如 vLLM 课程优先使用 `review-vllm-courseware`，SGLang 课程优先使用 `review-sglang-courseware`。
4. 在生成正文前，完整阅读 [references/output-contract.md](references/output-contract.md)。

## 工作流

### 1. 明确范围与交付方式

识别以下输入：

- 原始飞书文档 URL 或 token。
- 目标章节、标题或 block 范围。
- 创建新文档还是更新已有面经文档。
- 技术校对基准，例如本地源码树、已安装软件包、论文或官方文档。

若章节范围可以从用户当前上下文唯一确定，直接执行。只有存在多个实质不同的章节候选时才询问用户。用户未指定输出位置时，在当前身份可创建的位置新建飞书 Docx。

不要修改原始文档，除非用户明确要求。

### 2. 读取原文并建立候选题台账

按以下顺序读取：

1. 用 `docs +fetch --scope outline --detail with-ids` 获取目录和章节 block ID。
2. 用 `docs +fetch --scope section --start-block-id <章节标题 ID> --detail full` 精读目标章节。
3. 对嵌入资源进行下钻读取；不能遗漏其中承载的关键对比表、公式或实现说明。

在内部建立题目台账，每题至少记录：

- `question`
- `source_heading`
- `source_block_id`
- `original_points`
- `verified_corrections`
- `answer`
- `interview_frequency`：`high` / `medium` / `low`
- `vllm_importance`：`high` / `medium` / `low` / `not_applicable`
- `selection_reason`
- `dedup_key`

候选题必须能在目标章节中找到明确依据。允许把陈述句改写成面试问题，但不要引入章节之外的新主题。先完整收集定义、原理、流程、公式、算法对比、工程实现、边界条件和评估指标等候选，再按下一步的门槛筛选。

### 3. 筛选常考题与 vLLM 核心知识

每道最终入选题必须至少满足一个条件：

- **面试常考**：能考察可迁移的核心能力，例如概念与原理、正确性保证、性能瓶颈、关键流程、方案对比、工程权衡、常用配置或典型故障分析；面试官可以据此继续追问“为什么、怎么实现、何时失效”。
- **vLLM 核心**：对理解或使用 vLLM 具有明显价值，例如请求生命周期、调度与 batching、Model Runner、Attention/KV Cache、内存管理、并行与通信、解码与采样、模型加载、量化、性能优化、关键配置或可观测性；该知识点会影响正确性、性能、兼容性、资源占用或排障。

只有 `interview_frequency=high` 或 `vllm_importance=high` 的候选才能独立成题。两个维度都为 `medium` / `low` 的内容只可作为高价值问题答案里的补充背景、实现细节或追问点，不单独使用三级标题。

排除只复述背景、无法独立成题、仅对应一次性辅助代码、只考冷门字段记忆、强依赖某个短期版本且缺少机制价值，或与其他问题高度重复的候选。相邻候选考察同一能力时合并成一题；一题包含多个可独立追问的核心能力时再拆分。每题只考察一个清晰的主问题。

默认不设题目数量的上限、下限或章节配额。保留所有通过上述门槛的题，不为了整数、版面对称或固定模板增删题目。只有用户明确指定题数时，才按重要性排序后截取；排序时优先 `interview_frequency=high` 或 `vllm_importance=high`，再考虑知识前置关系和章节顺序。

### 4. 校对技术事实

按以下证据优先级核对：

1. 用户指定的本地源码或当前安装包源码。
2. 用户指定的论文、规范或官方技术资料。
3. 原始飞书章节。

对版本相关实现，记录软件版本、源码路径或提交信息。只修改能被证据确认的错误；无法确认的外部结论保持克制，并在答案中使用“通常”“取决于 checkpoint/config”等准确限定，不自行补造结论。

原文与源码冲突时，保留原文的讲解顺序和术语，但把错误结论直接改成正确表述。不要在每个答案里写成审计报告；只有冲突本身具有面试价值时才使用“更准确地说”。

### 5. 生成适合口述的答案

尽量复用原文的术语、逻辑顺序、公式和例子，只删除重复铺垫并补足必要的因果关系。默认把单题控制在 1～3 分钟可口述的长度。

按语义组织自然段，不把结论、机制、流程和边界条件挤在一个长段落里。除非答案很短且只表达一个完整观点，否则每题通常使用 2～4 个 `<p>`：第一段带“面试回答：”标签并直接给结论；中间段解释机制、流程或关键细节；最后一段补充边界、代价或工程权衡。续写段不重复“面试回答：”标签。超过约 180 个非空白字符的答案不得只有一个段落；使用独立 `<p>` 分段，不用 `<br/>` 模拟分段，也不要把本应连贯的回答机械拆成项目符号。

直接陈述技术事实，不在面试答案里引用整理过程。禁止用“源文档 + 中/把……”一类来源自指结构引出结论，也禁止用“当前 + vLLM”一类无明确版本号的时态前缀；大小写和中间空格变化同样视为命中。版本相关结论应写明具体版本、源码提交或 checkpoint/config 条件；没有具体版本依据时，直接陈述稳定机制并使用“通常”“取决于配置”等限定。

按题型组织：

- 原理题：先给结论，再解释机制，最后说明成立条件。
- 流程题：按真实执行顺序回答，不遗漏停止条件、bonus 或恢复分支。
- 对比题：先给核心差异，再讲各自代价和适用条件。
- 代码题：使用当前源码中的真实类名、字段名、张量形状和分支条件。
- 性能题：同时讨论收益来源、额外成本与可能退化的场景。

不要把原文大幅改写成另一套措辞；也不要为了“忠于原文”保留已确认的事实错误。答案正文保持自然口语，不添加“背诵版”“标准答案”等空标签。

### 6. 建立逐题原文定位

为每题选择最精确且稳定的原文锚点：

- 问题覆盖整个小节时，链接到该小节标题 block。
- 问题来自具体公式、代码或段落时，链接到对应 block。
- 问题综合多个相邻段落时，链接到最近的共同小节标题。

链接格式为原文 URL 去除旧 fragment 后追加 `#<source_block_id>`。每题必须且只能有一个主要“原文定位”段落，题目、答案和链接保持连续排列。

### 7. 创建或更新飞书文档

使用 `lark-doc` 的 XML 工作流写入。新建文档时采用以下结构：

1. 文档标题。
2. 一个简洁的导读 callout。
3. 一张章节概览表。
4. 按知识层级划分的二级章节。
5. 每题使用三级标题，紧跟 1～4 个自然段组成的“面试回答”答案组，再接一段“原文定位”；长答案通常分成 2～4 段。
6. 必要时在末尾增加一小段回答策略。

沿用 [references/output-contract.md](references/output-contract.md) 中的样式，不堆叠 callout、分栏或颜色。长文档分章节顺序写入；更新已有文档时优先使用 `block_replace` 等精确操作，保留用户已有图片、链接、评论相关块和其他无关内容。

同一 Agent 串行执行文档写入。每次 `block_replace` 后把被替换的旧 block ID 视为失效；后续仍需操作该位置时先重新 fetch。

### 8. 验收

写完后重新 fetch 输出文档，逐项检查：

- 问题数量与答案数量一致。
- 每道题都满足“面试常考”或“vLLM 核心”至少一个入选条件，没有低价值填充题或近义重复题。
- 用户未指定题数时，最终题量由通过门槛的候选自然决定，没有固定上限、下限或章节配额。
- 每个问题后都有一个“面试回答”和一个“原文定位”。
- 超过约 180 个非空白字符的回答已经按语义拆成至少两个自然段，且只有首段带“面试回答：”标签。
- 题号连续，章节编号一致。
- 所有原文链接包含 fragment，且 fragment 对应源文档的真实 block ID。
- 答案不含来源自指结构或无明确版本号的时态前缀。
- 公式、代码和特殊字符没有因 XML 或 shell 转义损坏。
- 没有把已确认错误重新写回答案。
- 文档版式仍保持统一。

优先运行：

```bash
python3 scripts/validate_interview_doc.py \
  --doc '<输出文档 URL 或 token>' \
  --source-doc '<原始文档 URL 或 token>' \
  --expected-questions <题目数>
```

脚本通过后，再向用户交付可点击的飞书文档链接，并简要说明题目数、校对基准及主要修正类型。

## 失败处理

- 认证失败：读取 `lark-shared`，完成对应业务域授权后重试。
- 无读取权限：报告具体文档及权限问题，不猜测正文。
- 无写入权限：保留已生成的题目台账，询问用户提供可写目标位置或文档。
- 源码与版本不明：继续完成原文整理，但把技术修正限制为高置信度内容，并在交付中说明校对范围。
- 写入部分失败：重新 fetch 当前文档状态，只重试失败的最小 block，禁止用 `overwrite` 覆盖已经成功且包含资源的文档。
